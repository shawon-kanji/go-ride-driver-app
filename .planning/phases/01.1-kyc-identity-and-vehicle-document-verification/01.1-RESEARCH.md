# Phase 01.1: KYC — Identity & Vehicle Document Verification - Research

**Researched:** 2026-08-10
**Domain:** Expo/React Native document-capture-and-upload UI (presigned-URL flow) + local native Android build tooling + first-time Jest/RNTL test setup for this repo
**Confidence:** HIGH (backend contract, verified directly against source), HIGH (expo-image-picker/file-system APIs, verified against current npm registry + official docs), MEDIUM (jest-expo/jest pairing — Expo resolves this dynamically via `expo install`, no single hardcoded version is "correct"), MEDIUM (local Android target setup — verified against this exact machine's installed SDK, but AVD-vs-device tradeoff is a judgment call, not a fact)

## Summary

This phase is 100% client-side UI work against an already-complete, already-verified backend (`go-ride-backend`'s `application/kyc/*`, routes under `/api/v1/driver/kyc/*`). There is no ambiguity in the request/response contract — it was read directly from source, not inferred. The real work and real risk are: (1) wiring `expo-image-picker` capture results into a **raw, unauthenticated `PUT`** to a presigned S3-compatible URL whose `Content-Type` header must byte-for-byte match the `content_type` string sent when the URL was requested (S3 signs that header into the signature — a mismatch is a hard `403` from S3, not a friendly backend error), (2) standing up this repo's **first-ever** test infrastructure (zero Jest tooling exists today) in a way that's compatible with Expo SDK 57 / RN 0.86 / React 19.2 / expo-router, and (3) getting a runnable local Android target on a machine that has the SDK platform/build-tools but **no emulator and no AVD installed**.

`expo-image-picker@57.0.8` and the new `expo-file-system` `File`/`Blob`-interface API (paired with `expo/fetch`, built into the `expo` package already installed — no new dependency) is the cleanest, most current (SDK 54+) way to turn an `ImagePickerAsset`'s local `file://` uri into upload bytes: `new File(asset.uri)` directly implements the web `Blob` interface, so it can be passed straight into a `fetch(uploadUrl, { method: 'PUT', body: file, headers: { 'Content-Type': contentType } })` call — no manual base64/blob dance required. `jest-expo@57.0.3` (the `57.0.0` release had a peer-dependency conflict with RN 0.86 that's fixed as of `57.0.1`) plus `@testing-library/react-native@14.0.1` is the correct pairing for this stack; use `npx expo install jest-expo jest --dev` rather than hand-pinning `jest`'s version, since Expo's installer resolves the exact compatible `jest` major for you (jest-expo's own bundled sub-packages point at the 29.x line, not 30.x — verify what gets resolved rather than assuming).

**Primary recommendation:** Use `expo-image-picker` + `expo-file-system`'s `File` class + the built-in `expo/fetch` for capture-to-upload; test with `jest-expo@^57.0.3` + `@testing-library/react-native@^14.0.1` using manual `jest.spyOn(global, 'fetch')`/module mocks (no extra mocking library needed); get a runnable Android target via a **physical device over USB debugging** (camera-capture flows are the actual feature under test — an emulator's fake camera feed is a worse test double here than on other phases), with the AVD path (`sdkmanager`/`avdmanager`, `x86_64` system image — this machine reports `uname -m` = `x86_64`, i.e. Intel, not Apple Silicon) documented as a fallback.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Document capture flow**
- Use `expo-image-picker` (not `expo-camera`) for all 10 document types — it provides both `launchCameraAsync` and `launchImageLibraryAsync` without building a custom camera UI, minimizing new native surface in a local-build-only (no EAS) setup.
- Each document tile's primary action opens the camera directly (`launchCameraAsync`); a secondary "Choose from gallery" affordance is available on the same capture screen for retakes/existing scans.
- Selected as recommended default — camera-first matches how document-verification flows are normally used (fresh photo, not old gallery images), gallery stays available as an explicit fallback.

**Navigation entry point**
- Add a 4th bottom tab, "Verify" (alongside Home / Vehicles / Profile), rather than nesting KYC under Profile or only reaching it from Home.
- Selected as recommended default — KYC status is a persistent, high-priority blocker until approved (blocks both vehicle activation and going online), consistent with how Vehicles/Profile already get dedicated tabs rather than being buried in a menu.
- Home screen's placeholder copy ("Going online is coming soon...") should be updated to reflect the real blocker once this phase exists, but the online-toggle UI itself is still Phase 2 — Home in this phase only needs a KYC-status summary card/banner linking to the Verify tab.

**Hub screen structure**
- Single "Verify" hub screen with document tiles grouped into two sections: **Identity** (5 tiles, always shown) and **Vehicle documents** (5 tiles per vehicle; if the driver has more than one vehicle, a vehicle picker/selector switches which vehicle's 5 tiles are shown — reuse the `Select` component pattern from vehicles feature).
- Tapping any tile (regardless of state) opens a focused single-document capture/detail screen for that one document type; not a linear multi-step wizard — documents can be completed or re-visited in any order.
- Tile states: not-uploaded (upload CTA), uploaded/in-review (pending badge), approved (checkmark badge, still tappable to view + re-upload), rejected (reason shown inline on the tile, re-upload CTA prominent).
- Re-uploading any document (including an already-approved one) is always allowed — the backend deliberately resets review state on re-upload (`is_current` supersede), so the UI doesn't need to block or specially gate this; a lightweight confirm ("This will need to be reviewed again") is enough for re-uploading an *approved* doc.
- Selected as recommended default — matches the two independent verification tracks in the backend's own data model (`driver_documents` scoped by `driver_id` vs `vehicle_id`) and supports out-of-order completion, which document-heavy onboarding flows need.

**Blocked-state messaging (KYC-04)**
- When `PATCH /driver/online` or `POST /vehicles/{id}/activate` returns `403 KYC_NOT_APPROVED` or `403 VEHICLE_NOT_VERIFIED` (both already implemented server-side), show an inline banner/dialog at the point of the blocked action (not a generic toast) that names specifically what's missing (identity vs. this vehicle's documents) and includes a direct CTA that navigates into the Verify tab.
- Selected as recommended default — KYC-04 explicitly requires this clarity; a generic error would leave the driver stuck without knowing what to do next. Consumed again by Phase 2's online-toggle blocked state and by Phase 1's existing vehicle-activate confirm-dialog flow (`ConfirmDialog` component already used there).

### Request/response shapes

```typescript
// POST /driver/kyc/documents/upload-url
interface RequestUploadURLRequest {
  document_type: string;      // one of the 10 above
  content_type: string;       // MUST exactly match the Content-Type header sent on the PUT — S3 signs this into the URL
  vehicle_id?: string;        // REQUIRED (UUID) for the 5 vehicle-scoped types, FORBIDDEN (must be omitted, not empty string) for the 5 identity types
}
interface RequestUploadURLResponse {
  upload_url: string;         // presigned S3 PUT URL, 15-minute expiry (S3Storage.defaultPresignExpiry)
  key: string;                // echo this back verbatim on confirm
}

// POST /driver/kyc/documents/confirm
interface ConfirmUploadRequest {
  document_type: string;
  key: string;                // must be the exact key from upload-url's response
  vehicle_id?: string;        // same required/forbidden rule as above
}
interface DocumentResponse {
  id: string;
  document_type: string;
  vehicle_id?: string;
  status: 'uploaded' | 'approved' | 'rejected';
  rejection_reason?: string;
}

// GET /driver/kyc/status
interface KycStatusResponse {
  kyc_status: 'not_started' | 'in_review' | 'approved' | 'rejected';
  documents: DocumentResponse[];  // only CURRENT documents (is_current=true) — a re-uploaded doc's prior row won't appear
}
```

**Object key scheme** (server-generated, client never constructs this — just echoes it back): `drivers/{driverID}/{documentType}/{uuid}` for identity docs, `drivers/{driverID}/{documentType}/{vehicleID}/{uuid}` for vehicle-scoped docs.

**Validation enforced server-side** (`application/kyc/validation.go`) — replicate client-side for fail-fast UX, but the server is the real gate:
- `document_type` must be one of the 10 canonical values.
- `vehicle_id` required+valid-UUID for the 5 vehicle-scoped types; must be entirely absent (not `""`) for the 5 identity types — sending an empty string for an identity type will fail validation the same as sending a real UUID.

**Error codes to recognize (KYC-04)** (`pkg/apperror/errors.go`, flat `{code, message}` shape — matches this app's existing `ApiErrorBody`/`ApiError`):

| Code | HTTP | When |
|------|------|------|
| `KYC_NOT_APPROVED` | 403 | Driver identity `kyc_status != approved`, blocking `PATCH /driver/online` or `POST /vehicles/{id}/activate` |
| `VEHICLE_NOT_VERIFIED` | 403 | Target vehicle missing an approved current row for one of its 5 required document types |
| `VALIDATION_ERROR` | 400 | Bad `document_type`/`vehicle_id` combination on upload-url or confirm |
| `DOCUMENT_FORBIDDEN` | 403 | Confirming an upload for a vehicle the driver doesn't own |
| `UPLOAD_NOT_CONFIRMED` | 400 | `confirm` called but the S3 `HeadObject` check found nothing at `key` (PUT never actually landed) |

### The upload flow, step by step

1. `POST upload-url` with `{document_type, content_type, vehicle_id?}` → `{upload_url, key}`. **No file bytes involved yet — this step is pure JSON over `apiRequest`, same as any other endpoint.**
2. Raw `PUT upload_url` with the file bytes as body, `Content-Type` header set to the **exact same string** sent as `content_type` in step 1. **No `Authorization` header, no `application/json` Content-Type, no envelope** — this is a direct-to-S3 request, not a call to `go-ride-backend`. Using `apiRequest()` here is a bug (it force-sets `Content-Type: application/json` and injects a `Bearer` token that S3 doesn't expect and doesn't want).
3. `POST confirm` with `{document_type, key, vehicle_id?}` (same `key` from step 1) → `DocumentResponse`. Server does a `HeadObject` existence check before creating the row — the driver cannot spoof "uploaded" without actually having PUT bytes to that key.
4. Once all 5 identity types have a current row, `drivers.kyc_status` auto-flips `not_started → in_review` (server-side, automatic — the client does nothing extra to trigger this). Vehicle-scoped uploads never touch `kyc_status`.
5. **Re-upload semantics**: uploading a new document in the same scope (`driver_id`+`document_type` for identity, `vehicle_id`+`document_type` for vehicle docs) supersedes the prior row (`is_current=false`) rather than overwriting it — history is preserved server-side. Re-uploading an **approved** identity document pulls `kyc_status` back to `in_review`; re-uploading a vehicle document un-derives that vehicle's "verified" status the moment its current row's `status` isn't `approved`. **The UI does not need to do anything special to trigger this — it's automatic on `confirm`.** This is why CONTEXT.md's decision to always allow re-upload (even on approved docs) with just a lightweight confirm is correct and requires no extra client-side state machine.
6. Approval/rejection is **manual SQL only** — no endpoint exists, no polling will ever surface a status change faster than an operator's `UPDATE`. Don't build any "waiting for review" animation more elaborate than a static pending badge.

### Pattern 1: Composed upload mutation (3 network calls presented as 1 to the UI)

**What:** A single TanStack Query mutation hook (`useUploadDocumentMutation`) that internally sequences `requestUploadUrl → PUT → confirmUpload`, exposing one `mutate()`/`isPending`/`onError` surface to the document capture screen — the screen never juggles 3 separate loading states.
**When to use:** Every document upload in this phase — there is no scenario where a caller wants only 1 or 2 of the 3 steps.
**Example:**
```typescript
// src/features/kyc/api.ts
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { kycClient } from '../../api/kyc-client';
import { putDocumentBytes } from '../../api/kyc-upload';
import type { DocumentType } from '../../api/types';

interface UploadDocumentInput {
  documentType: DocumentType;
  vehicleId?: string;
  fileUri: string;
  contentType: string; // from ImagePickerAsset.mimeType, with a fallback — see Pitfalls
}

export function useUploadDocumentMutation() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async ({ documentType, vehicleId, fileUri, contentType }: UploadDocumentInput) => {
      const { upload_url, key } = await kycClient.requestUploadUrl({
        document_type: documentType,
        content_type: contentType,
        vehicle_id: vehicleId,
      });
      await putDocumentBytes(upload_url, fileUri, contentType);
      return kycClient.confirmUpload({ document_type: documentType, key, vehicle_id: vehicleId });
    },
    onSuccess: () => queryClient.invalidateQueries({ queryKey: kycKeys.status() }),
  });
}
```

### Pattern 2: Raw PUT helper isolated from `apiRequest`

**What:** A dedicated, tiny function that does the S3 PUT — never routed through `apiRequest()`, which would incorrectly attach a `Bearer` token and force `Content-Type: application/json`.
**Example (using the recommended `expo-file-system` + `expo/fetch` approach):**
```typescript
// src/api/kyc-upload.ts
import { fetch } from 'expo/fetch';
import { File } from 'expo-file-system';

export async function putDocumentBytes(
  uploadUrl: string,
  fileUri: string,
  contentType: string,
): Promise<void> {
  const file = new File(fileUri); // wraps the local file:// uri from ImagePickerAsset.uri
  const response = await fetch(uploadUrl, {
    method: 'PUT',
    headers: { 'Content-Type': contentType }, // MUST exactly match what was sent to /upload-url
    body: file, // File implements Blob — no manual base64/blob conversion needed
  });
  if (!response.ok) {
    // S3 errors are XML, not the backend's {code, message} shape — don't parse as ApiErrorBody
    throw new Error(`Upload failed with status ${response.status}`);
  }
}
```

### Pattern 3: `document_type` → `vehicle_id` requirement as a lookup table, not scattered `if`s

**What:** A single source of truth (`isVehicleDocumentType(type)`) mirroring `domain/kyc.IsVehicleDocumentType` exactly, used everywhere the client needs to decide whether to send/require `vehicle_id` — capture screen, upload mutation input validation, hub screen section grouping.
**When to use:** Anywhere `document_type` is handled — never re-derive this from a hardcoded string list inline.

### Anti-Patterns to Avoid

- **Routing the raw PUT through `apiRequest()`:** it force-injects `Authorization` and `Content-Type: application/json`, both wrong for a presigned S3 PUT and will produce a signature mismatch (`403` from S3) or reject the object type server never expects.
- **Treating `content_type` as a free client choice:** whatever string is sent to `/upload-url` MUST be the exact `Content-Type` header on the PUT. Don't default to `'application/octet-stream'` on one side and `'image/jpeg'` on the other — pick one source (e.g., `asset.mimeType` with a well-defined fallback) and use it for both calls in the same upload.
- **Polling `/driver/kyc/status` on an interval "just in case":** approval is manual-SQL-only (see Backend Contract step 6) — nothing changes between an app open and a refetch-on-focus; a polling loop burns battery/requests for zero benefit. Refetch on screen focus / after a mutation succeeds, not on a timer.
- **Building a linear multi-step wizard:** CONTEXT.md explicitly rejects this — each document tile is independently tappable/completable, matching the backend's two independent tracks (driver-level vs. vehicle-level rows).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Converting a picked image's local uri into upload-ready bytes | Manual `FileReader`/base64 read-and-decode pipeline | `expo-file-system`'s `File` class (implements `Blob`) | `File` already implements the web `Blob` interface — passing it directly as a `fetch` body is supported natively by `expo/fetch`; hand-rolling this reintroduces exactly the base64-memory-overhead problem the new API was built to remove |
| Camera/gallery picker UI | Custom `expo-camera`-based capture screen | `expo-image-picker`'s `launchCameraAsync`/`launchImageLibraryAsync` | Already locked in CONTEXT.md — provides OS-native camera UI (including its own permission flow) with zero custom native surface, appropriate for a local-build-only, no-EAS project |
| Determining whether a document is "vehicle-scoped" | Ad hoc string checks (`type.startsWith('vehicle_')`) scattered across components | A single constant array mirroring `domain/kyc.RequiredVehicleDocumentTypes`, checked via one helper | The backend's own `IsVehicleDocumentType` is the actual source of truth; string-prefix guessing would silently drift if the backend ever adds a non-`vehicle_`-prefixed vehicle-scoped type |
| Retry/backoff on the raw PUT | Custom retry loop with manual backoff timers | TanStack Query's built-in mutation retry (`retry: N` option) or a simple manual "Retry" button surfaced via `mutation.isError` | Mutation retry semantics (don't retry a 4xx signature mismatch, do retry a network blip) are exactly what Query's `retry` predicate option is for; hand-rolled timers duplicate this for no benefit |

**Key insight:** everything in this phase that looks like it needs custom infrastructure (upload plumbing, status tracking, retry) already has a first-class primitive in the stack this project already committed to (TanStack Query, `expo-file-system`'s new API) — the actual net-new code is thin glue, not infrastructure.

## Common Pitfalls

### Pitfall 1: `Content-Type` mismatch between `upload-url` request and the PUT header

**What goes wrong:** The presigned URL's signature is computed over the `content_type` sent to `/upload-url`. If the PUT's actual `Content-Type` header differs by even a charset parameter or casing quirk in some S3-compatible implementations, S3 rejects the PUT with a signature-mismatch error — which surfaces to the app as an opaque failed `fetch`, not a friendly backend error (the backend never sees this call at all).
**Why it happens:** `ImagePickerAsset.mimeType` can be `null` on some Android devices/gallery sources, tempting a fallback that differs between the two call sites (e.g., inferring from file extension differently in two places).
**How to avoid:** Compute `contentType` exactly once per upload (e.g., `asset.mimeType ?? 'image/jpeg'`, since `launchCameraAsync`/`launchImageLibraryAsync` restricted to `mediaTypes: ['images']` will essentially always be JPEG/PNG from a camera) and pass that single value into both the `requestUploadUrl` call and `putDocumentBytes` — never recompute it a second time.
**Warning signs:** Uploads that fail only for gallery-picked images (where `mimeType` is more often `null`) but work for fresh camera captures.

### Pitfall 2: `vehicle_id` sent as `""` instead of omitted for identity documents

**What goes wrong:** The backend's validation treats a present-but-empty `vehicle_id` as a violation for identity document types (`vehicle_id must not be set for this document type`) — same failure class as sending a real UUID. A naive DTO builder that always includes `vehicle_id: selectedVehicleId ?? ''` will break every identity upload.
**Why it happens:** JS/TS makes it easy to always include an optional field with an empty-string default rather than conditionally omitting the key.
**How to avoid:** Build the request body conditionally — only include `vehicle_id` in the object at all when `isVehicleDocumentType(documentType)` is true. Cover this with a unit test per document type category (see Validation Architecture below).

### Pitfall 3: `jest-expo@57.0.0` peer-dependency conflict with this repo's RN `0.86.2`

**What goes wrong:** Installing `jest-expo` without pinning `^57.0.1`+ can resolve `57.0.0`, whose peer dep on `@react-native/jest-preset@^0.85.0` conflicts with RN `0.86.2`'s own `@react-native/jest-preset@0.86.0`, causing an npm install failure or requiring `--legacy-peer-deps`.
**Why it happens:** This was a genuine upstream bug (fixed in `jest-expo@57.0.1`), not user error — but `npm install jest-expo` without a version range could still resolve an old cached/pinned `57.0.0` in some lockfile scenarios.
**How to avoid:** Explicitly install `jest-expo@^57.0.3` (or later, always ≥57.0.1); verify `npm ls jest-expo @react-native/jest-preset` shows no conflict after install.

### Pitfall 4: Test files placed inside `src/app/` break expo-router

**What goes wrong:** expo-router treats every file inside `src/app/` as a route or layout. A `.test.tsx` file dropped next to `verify/index.tsx` will be picked up by the router itself (not just Jest), producing a broken/duplicate route or a build-time error.
**How to avoid:** Keep all test files in `__tests__/` (or feature-colocated `*.test.ts(x)` outside `src/app/`, e.g. `src/features/kyc/api.test.ts`) — never inside `src/app/`.

### Pitfall 5: `@testing-library/react-native@14` hides expo-router's own extended jest matchers (`toHavePathname`, etc.)

**What goes wrong:** RNTL v14 changed how it exposes its matcher-extension mechanism, and expo-router's `expo-router/testing-library` matchers (`toHavePathname`, `toHaveSearchParams`) stopped resolving on top of it in some combinations — reported as `expo/expo` community issue, closed "not planned" by RNTL maintainers as of research date.
**Why it happens:** Cross-package matcher registration order changed between RNTL v13 and v14; expo-router's testing-library package hasn't been updated to match.
**How to avoid:** This phase's tests are overwhelmingly component/hook-level (`DocumentTile`, `useUploadDocumentMutation`, capture-flow helpers), not route-navigation assertions — avoid depending on `expo-router/testing-library`'s custom matchers for this phase's test suite; use plain `@testing-library/react-native` queries (`getByText`, `getByRole`) and, where a route push needs verifying, assert on the mocked `expo-router`'s `router.push` call arguments instead of `toHavePathname`.
**Warning signs:** `TypeError: screen.getPathname is not a function` or similar when a test imports from `expo-router/testing-library`.

### Pitfall 6: `expo-image-picker`'s config plugin change requires a full native rebuild, not a JS reload

**What goes wrong:** Adding `expo-image-picker` to `app.json`'s `plugins` array (needed to customize `cameraPermission`/`photosPermission` copy, and to opt out of the default `RECORD_AUDIO` permission this library adds even though this phase never records audio/video) only takes effect after regenerating the native Android project — this repo's own `PITFALLS.md` Pitfall 7 flags exactly this class of mistake. A stale dev client (or `npx expo run:android` skipped after the plugin config change) will silently keep the old permission set, and Metro hot-reload gives a false sense that the change "worked."
**How to avoid:** Any time the `expo-image-picker` plugin config block changes, run `npx expo run:android` again (full native rebuild) before trusting a test result — don't rely on `expo start` against an already-built dev client.

### Pitfall 7: No Android emulator/AVD installed on this machine, and this phase's core feature (camera capture) tests poorly on one anyway

**What goes wrong:** `emulator` and all `system-images` packages are absent from the installed SDK (`platforms` android-35/36 and `build-tools` 35.0.0/36.0.0 are present, but nothing under `emulator/` and `sdkmanager --list_installed` shows no system images) — `npx expo run:android` will fail immediately with no target device/emulator to install to.
**How to avoid:** Two paths, pick one:
  - **Physical device (recommended for this phase specifically):** Enable Developer Options + USB debugging on an Android phone, connect via USB, confirm `adb devices` lists it, then `npx expo run:android` targets it directly. No new SDK packages needed (`platform-tools`/`adb` already present and working — confirmed via `adb devices` during this research). Strictly better for this phase because document capture UX (autofocus, real lighting, actual document photos) cannot be meaningfully exercised through an emulator's synthetic camera feed anyway.
  - **AVD fallback (e.g., no physical device available):** This machine is `x86_64` (Intel, not Apple Silicon — confirmed via `uname -m`), so the system image ABI must be `x86_64`, not `arm64-v8a`:
    ```bash
    sdkmanager --install "emulator" "system-images;android-35;google_apis;x86_64"
    avdmanager create avd -n driver_test -k "system-images;android-35;google_apis;x86_64" --device "pixel_6"
    "$ANDROID_HOME/emulator/emulator" -avd driver_test
    ```
    Requires accepting the relevant SDK license (`sdkmanager --licenses`) if not already accepted — `licenses/` directory already shows several accepted licenses on this machine, but `android-sdk-preview-license`/system-image-specific ones may still prompt.
**Warning signs:** `npx expo run:android` failing with "no devices/emulators found" before any of this phase's actual code is even exercised.

// src/features/kyc/document-capture.ts
import * as ImagePicker from 'expo-image-picker';

export async function captureFromCamera(): Promise<ImagePicker.ImagePickerAsset | null> {
  const { granted } = await ImagePicker.requestCameraPermissionsAsync();
  if (!granted) return null;

  const result = await ImagePicker.launchCameraAsync({
    mediaTypes: ['images'], // stills only — this phase never handles video
    quality: 1,
  });
  return result.canceled ? null : (result.assets[0] ?? null);
}

export async function pickFromLibrary(): Promise<ImagePicker.ImagePickerAsset | null> {
  const { granted } = await ImagePicker.requestMediaLibraryPermissionsAsync();
  if (!granted) return null;

  const result = await ImagePicker.launchImageLibraryAsync({ mediaTypes: ['images'] });
  return result.canceled ? null : (result.assets[0] ?? null);
}

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|---------------|--------|
| `expo-file-system`'s legacy flat function API (`FileSystem.readAsStringAsync`, string-uri-based) | `File`/`Directory` object API implementing web `Blob`/`Uint8Array` interfaces | SDK 54 (per Expo's own blog post) | Direct `fetch(url, { body: file })` support without manual base64 conversion — this is the pattern this phase should use, not the legacy string-based reads still found in older tutorials |
| `expo-image-manipulator`'s `manipulateAsync()` | Context-based chainable API: `ImageManipulator.manipulate(uri).resize(...).renderAsync()` then `.saveAsync()` | Recent `expo-image-manipulator` major (current `57.0.8` line) | `manipulateAsync` is marked deprecated in current docs; don't build new code against it if this phase's discretionary resize feature is picked up |
| `@testing-library/jest-native` for custom matchers (`toBeVisible`, etc.) | Built into `@testing-library/react-native` v12.4+ directly, no separate package | v12.4+ | Don't add `@testing-library/jest-native` as a dependency — it's deprecated and its matchers are already included |

**Deprecated/outdated:**
- `expo-file-system`'s old string-URI functions: still present for backward compat but not what new code (this phase) should be written against.
- `manipulateAsync` in `expo-image-manipulator`: deprecated, still functional in `57.0.8`.
- `@testing-library/jest-native`: unmaintained, superseded by RNTL's built-in matchers.

## Open Questions

1. **Should client-side image resize (`expo-image-manipulator`) be included in this phase?**
   - What we know: The backend enforces no file size limit; the new context-based `manipulate()` API is confirmed SDK-57-compatible and straightforward (`resize({width, height}).renderAsync().saveAsync({format, compress})`).
   - What's unclear: Whether the added complexity (a resize step in the capture flow, plus its own set of edge cases — aspect ratio math, EXIF orientation handling on Android which has historically been finicky with manipulator libraries) is worth it for a first version, given camera-first capture already produces "fresh" (not enormous multi-generation-compressed) photos and this repo has no network-speed complaints yet to react to.
   - Recommendation: **Defer to a follow-up** unless slow-upload complaints materialize in testing — ship the direct-PUT flow first (already correctly scoped as Claude's discretion in CONTEXT.md, not a locked requirement), and revisit if 8-12MP camera photos (typically 3-8MB) prove painfully slow on realistic mobile upload speeds during manual verification.

2. **Exact `jest` version that `npx expo install jest-expo jest --dev` will resolve for this SDK.**
   - What we know: `jest-expo@57.0.3`'s own bundled dependencies (`jest-snapshot`, `babel-jest`, `@jest/globals` at `^29.2.1`) strongly suggest the paired `jest` major is 29.x, not the current `jest@30.4.2` "latest".
   - What's unclear: Expo's installer resolves this from a server-side compatibility table not queried directly in this research pass (the `exp.host` versions API queried didn't return a usable match for this specific lookup).
   - Recommendation: Run `npx expo install jest-expo jest --dev` at Wave 0 and record what actually resolves (`npm ls jest jest-expo`) rather than hand-pinning a guessed version — treat the resolved version as ground truth for the rest of the phase's test setup.

3. **`transformIgnorePatterns` exact current value for SDK 57.**
   - What we know: The general shape (a regex excluding `react-native`/`expo`/`@react-navigation` family packages from being ignored by the transformer) is stable across SDKs and documented above.
   - What's unclear: `jest-expo`'s preset (`jest-expo/jest-preset.js`) typically already bakes in a correct `transformIgnorePatterns` when used via `preset: 'jest-expo'` alone — the explicit override shown in Code Examples may be unnecessary or could even conflict with what the preset already sets.
   - Recommendation: Try `preset: 'jest-expo'` with **no** explicit `transformIgnorePatterns` override first at Wave 0; only add an override if a real "Cannot use import statement outside a module" failure surfaces against a specific package (e.g., if `nativewind` or `zustand` need adding to the pattern).
