# Phase 01.1: KYC — Identity & Vehicle Document Verification - Context

**Gathered:** 2026-08-10 (via `/gsd:discuss-phase 01.1 --auto`)
**Status:** Ready for planning

<domain>
## Phase Boundary

Driver can upload their identity documents (selfie, govt ID front/back, driving license front/back) and, per vehicle, that vehicle's 5 required documents (registration, photo front/back/side, number plate); can view current KYC/document status including rejection reasons; can re-upload a rejected (or already-approved) document; and sees a clear explanation — not a raw 403 — when blocked from activating a vehicle or going online because KYC is incomplete. Backend (upload-url/confirm/status endpoints, gating logic, storage) is 100% already built — this phase is driver-app UI/client only. No backoffice/reviewer UI or endpoint (approvals stay manual SQL, by explicit choice). Going online itself and the map are Phase 2, out of this phase's scope.

</domain>

<decisions>
## Implementation Decisions

### Document capture flow
- Use `expo-image-picker` (not `expo-camera`) for all 10 document types — it provides both `launchCameraAsync` and `launchImageLibraryAsync` without building a custom camera UI, minimizing new native surface in a local-build-only (no EAS) setup.
- Each document tile's primary action opens the camera directly (`launchCameraAsync`); a secondary "Choose from gallery" affordance is available on the same capture screen for retakes/existing scans.
- `[auto]` Selected as recommended default — camera-first matches how document-verification flows are normally used (fresh photo, not old gallery images), gallery stays available as an explicit fallback.

### Navigation entry point
- Add a 4th bottom tab, "Verify" (alongside Home / Vehicles / Profile), rather than nesting KYC under Profile or only reaching it from Home.
- `[auto]` Selected as recommended default — KYC status is a persistent, high-priority blocker until approved (blocks both vehicle activation and going online), consistent with how Vehicles/Profile already get dedicated tabs rather than being buried in a menu.
- Home screen's placeholder copy ("Going online is coming soon...") should be updated to reflect the real blocker once this phase exists, but the online-toggle UI itself is still Phase 2 — Home in this phase only needs a KYC-status summary card/banner linking to the Verify tab.

### Hub screen structure
- Single "Verify" hub screen with document tiles grouped into two sections: **Identity** (5 tiles, always shown) and **Vehicle documents** (5 tiles per vehicle; if the driver has more than one vehicle, a vehicle picker/selector switches which vehicle's 5 tiles are shown — reuse the `Select` component pattern from vehicles feature).
- Tapping any tile (regardless of state) opens a focused single-document capture/detail screen for that one document type; not a linear multi-step wizard — documents can be completed or re-visited in any order.
- Tile states: not-uploaded (upload CTA), uploaded/in-review (pending badge), approved (checkmark badge, still tappable to view + re-upload), rejected (reason shown inline on the tile, re-upload CTA prominent).
- Re-uploading any document (including an already-approved one) is always allowed — the backend deliberately resets review state on re-upload (`is_current` supersede), so the UI doesn't need to block or specially gate this; a lightweight confirm ("This will need to be reviewed again") is enough for re-uploading an *approved* doc.
- `[auto]` Selected as recommended default — matches the two independent verification tracks in the backend's own data model (`driver_documents` scoped by `driver_id` vs `vehicle_id`) and supports out-of-order completion, which document-heavy onboarding flows need (driver may have some documents ready before others).

### Blocked-state messaging (KYC-04)
- When `PATCH /driver/online` or `POST /vehicles/{id}/activate` returns `403 KYC_NOT_APPROVED` or `403 VEHICLE_NOT_VERIFIED` (both already implemented server-side, see canonical refs), show an inline banner/dialog at the point of the blocked action (not a generic toast) that names specifically what's missing (identity vs. this vehicle's documents) and includes a direct CTA that navigates into the Verify tab.
- `[auto]` Selected as recommended default — KYC-04 explicitly requires this clarity; a generic error would leave the driver stuck without knowing what to do next. This decision matters now (for this phase's status/error display) and will be consumed again by Phase 2's online-toggle blocked state and by Phase 1's existing vehicle-activate confirm-dialog flow (`ConfirmDialog` component already used there).

### Claude's Discretion
- Exact permission-prompt copy for camera/media-library access.
- Whether to compress/resize images client-side before the presigned PUT (backend doesn't enforce a size limit today; a reasonable default — e.g. `expo-image-manipulator` resize to a max dimension — avoids slow uploads on large phone camera photos, but isn't a locked requirement).
- Upload progress indicator design and retry behavior on network failure during the PUT step.
- Exact visual styling/polish — per Phase 1's precedent, the "bold/vibrant" brand identity (PROJECT.md) is deferred to a dedicated future UI-spec pass; this phase uses the same standard, clean conventions and existing primitives (`Card`, `Badge`, `Banner`, `Button`, `ConfirmDialog`, `EmptyState`, `Select`) as Phase 1.
- Internal file/module organization within `src/features/kyc/` — mirrors the existing `src/features/vehicles/` shape (`api.ts`, `schemas.ts`, `components/`).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/components/{Card,Badge,Banner,Button,ConfirmDialog,EmptyState,Select}.tsx` — all directly reusable for document tiles (Card+Badge), status banners (Banner), re-upload confirm (ConfirmDialog), vehicle picker (Select), zero-documents state (EmptyState).
- `src/api/http-client.ts` (`apiRequest<T>()`) — reuse for `upload-url`, `confirm`, and `status` calls (JSON, auth header). **Do not reuse for the actual file PUT** — that's a raw `fetch(uploadUrl, {method: 'PUT', body: fileBytes})` with no `Authorization` header and no `Content-Type: application/json`; needs a small dedicated upload helper, not `apiRequest`.
- `src/features/vehicles/api.ts` + `src/api/vehicles-client.ts` — the query/mutation pattern to mirror exactly for `src/features/kyc/api.ts` + `src/api/kyc-client.ts` (query key factory, `useQuery`/`useMutation`, cache invalidation on mutation success).
- `src/api/types.ts` — extend with `KycStatus`, `DocumentType`, `DocumentStatus`, `Driver.kyc_status` (currently missing from the `Driver` interface).

### Established Patterns
- Per-domain split: `src/api/<domain>-client.ts` (raw endpoint calls) + `src/features/<domain>/api.ts` (TanStack Query hooks) + `src/features/<domain>/schemas.ts` (zod) + `src/features/<domain>/components/*` — same shape for `kyc` as `vehicles`/`profile`.
- Separate view/edit screens pattern (Phase 1: profile view → edit; vehicle list → detail/edit) — applies here as hub (view/list) → per-document capture screen (edit/upload), not inline editing on the hub.
- Confirm-dialog-before-consequential-action pattern (vehicle activate swap) — reused for re-uploading an already-approved document.

### Integration Points
- New 4th tab: `src/app/(app)/(tabs)/verify/` (or similar), added to `src/app/(app)/(tabs)/_layout.tsx` tab list.
- Vehicle detail screen (`src/app/(app)/(tabs)/vehicles/[id].tsx`) gets a new "Verify documents" action linking into the Verify tab, pre-selecting that vehicle.
- Home screen (`src/app/(app)/(tabs)/index.tsx`) placeholder copy and the (Phase 1) vehicle-activate error handling both need to route through the new KYC-error-recognition logic (KYC-04) — Phase 1 left "surfacing `KYC_NOT_APPROVED`/`VEHICLE_NOT_VERIFIED` distinctly" as Claude's discretion; this phase resolves that discretion point.
